# 운영 절차 (2026-11-25)

홈페이지를 고치고 올릴 때, 사람 · 에이전트 모두 이 순서를 따른다. 옛 문서(개발지침서.md · docs/ROLLBACK.md · .env.example)는 Vercel 시절 기준이라 맞지 않는다.

## 1. 배포 — 고친 것을 올리기

| 무엇 | 어디에 올리나 | 올린 뒤 확인 |
|---|---|---|
| 화면(html · js · css) | `git push origin main` → GitHub Pages(1~3분) | `curl https://k-logos.com/js/<파일>?cb=1` 에 새 판 번호(`console.log('[파일] v…')`)가 보이는지 |
| DB(SQL) | 아래 3번 절차 | `select … from public.schema_log` 에 그 파일이 있는지 |
| 파일 워커 `cloudflare/worker.js` | Cloudflare ▸ Workers ▸ church-files ▸ 코드 편집 → 붙여 넣고 「배포」 | `https://church-files.kds08200820.workers.dev/version` 의 판 번호 = 파일의 `WORKER_VERSION` |
| 재정 Apps Script `apps-script/finance-api.gs` | Apps Script 편집기(Code.gs) → 저장 → 배포 ▸ 배포 관리 ▸ 수정 ▸ 새 버전 | 웹앱 주소를 그냥 열면 나오는 `version` = 파일의 `API_VERSION` |
| 푸시 Apps Script(`*-push.gs`) | 같은 프로젝트에 파일 추가 · 고침 → 저장(트리거 함수는 한 번 실행) | 실행 로그 |
| Edge Function(`supabase/functions/*`) | Supabase ▸ Edge Functions ▸ 함수 ▸ Code ▸ Deploy updates | 대시보드 코드가 파일과 같은지 |
| 교회 PC 워커(`tools/*.py`) | 저장소는 OneDrive 로 교회 PC 에 따라간다 → **워커 창을 닫고 다시 켜야** 새 코드가 돈다 | 대시보드 「해야 할 일」에 「교회 PC 워커」가 안 뜨는지 |

- 올리기 전: `node tools/sqltest/run-all.mjs`(시험 전부) — GitHub 에 올리면 Actions 가 같은 검사를 자동으로 돌린다(실패하면 메일).
- 스키마가 바뀌는 화면은 SQL 을 먼저 실행한 뒤 올린다. SQL 이 없을 때도 화면이 조용히 버티게 만든다.
- 하루에 여러 번 올리기보다, 묶어서 시험한 뒤 올린다.

## 2. 되돌리기

- 화면: `git revert <커밋>` → push (force push 금지).
- DB: SQL 파일 머리의 「되돌리는 방법」대로. 트리거로 막은 것은 트리거만 지우면 예전처럼 움직이게 만들어 두었다.
- 자료: `docs/백업과-복구.md` (Supabase 자동 백업 7일치 · 주간 내려받기).
- 파일 워커 · Apps Script: 대시보드의 이전 버전(Cloudflare 「배포」 목록 · Apps Script 「배포 관리」의 버전)으로 되돌린다.

## 3. SQL 실행과 기록

1. `supabase/YYYYMMDD_HHMM_설명.sql` 로 쓴다. 맨 끝에 기록 한 줄:
   `insert into public.schema_log(file) values ('<파일 이름>') on conflict (file) do update set applied_at = now();`
2. `tools/sqltest/` 에 PGlite 시험을 두고 통과시킨다.
3. 커밋 · push 한 뒤, SQL 편집기에 **파일 내용 그대로** 넣고 파일과 같은지 확인한 다음 Run.
   - `drop` · `delete from` · `truncate` 가 든 파일은 편집기가 「Potential issue detected」를 띄운다 → 사람이 내용을 보고 직접 누른다.
     그래서 지우는 문장은 따로 떼어 「사람이 실행」 파일로 둔다(예: `20261125_1210_fin_clear_vouchers.sql`).
4. 실행 뒤 확인은 이름 · 건수만(교인 자료는 보지 않는다).
5. 무엇이 실행 안 됐는지: `node tools/schema-check.mjs` (사용자 환경변수 `SUPABASE_SERVICE_ROLE_KEY` 로 DB 의 *이름 목록*만 받아 SQL 파일과 견준다).
   「안 된 듯 · 일부만」은 사람이 열어 본다(뒤 파일이 이름을 바꾼 경우도 있다).

## 4. 교회 PC 워커 갱신

- 워커: `tools/ai_worker.py`(AI 답변 · 설교 PDF) · `tools/worship_worker.py`(주일 자료) · `tools/kakao_worker.py`(카카오톡 QT).
- 코드를 고쳤으면 교회 PC 에서 워커 창을 닫고 다시 켠다(작업 스케줄러에 걸린 것은 다시 시작).
- 살아 있는지: 워커가 5분마다 `church_settings` 의 `worker_ai` · `worker_worship` · `kakao_worker` 에 시각을 남긴다.
  AI · 주일 자료 워커는 40분, 아침에만 도는 카카오톡 워커는 26시간 넘게 끊기면 목회행정 대시보드 「해야 할 일」과 관리자 기기 푸시(`apps-script/worker-health-push.gs`, 밤 10시 ~ 아침 7시 제외)로 알린다.
- 카카오톡 예약 창에는 카카오톡 워커의 마지막 확인 시각이 보인다. 꺼져 있으면 정한 시각에 나가지 않는다.

## 5. 저장소를 OneDrive 밖으로 옮기기 (권장 — 각 PC 에서 사람이)

지금은 저장소와 `.git` 폴더(약 5.6GB)를 OneDrive 로 여러 PC 에 동기화한다. 두 PC 가 동시에 git 을 쓰면
커밋이 빠지거나 옛 파일이 되살아나고, `.git` 안에 충돌 사본(`index-당회실PC-6` 등)이 생긴다.

1. 각 PC 에서 아직 올리지 않은 것이 없는지: `git status` · `git log origin/main..HEAD` 가 비어 있어야 한다.
2. OneDrive 밖에 새로 받는다: `git clone https://github.com/kds08200820-del/woonpyung-church C:\work\woonpyung-church`
3. 교회 PC 의 워커 · 작업 스케줄러 · 바로가기가 가리키는 폴더를 새 자리로 바꾼다(예: `tools\카카오QT_발송.bat` 등록, 워커 실행 .bat).
4. 옛 OneDrive 폴더는 지우지 말고 이름만 바꿔 한 달 둔 뒤 정리한다.
5. 그 뒤로 PC 사이에는 GitHub 로만 주고받는다(`git pull` → 고침 → `git push`).
